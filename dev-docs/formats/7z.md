# 7z

Current maintainer truth for the 7z backend. A 7z archive does not hold members; it
holds a *decode program* — a graph of coders over packed byte slices — and a file table
that is laid onto that program's output by position. Most of what is peculiar here
follows from that. Registers keep the status — this page states the behaviour and links
the row.

## At a glance

| | |
| --- | --- |
| Read | Yes — native header parser, shared codec streams. No `py7zr` on the read path |
| Write | **Not shipped**, for any format — no `archivey.create`, no writer module ([writing design](../investigations/archive-writing-design.md)) |
| Source | Seekable only, in both access modes |
| Listing cost | `INDEXED` — with one exception the cost class cannot express: a symlink inside a solid folder decodes that whole folder while listing, unless `ArchiveyConfig.read_link_targets` is `False` (§2.2) |
| Access cost | `SOLID` when any folder carries more than one member, `DIRECT` otherwise. `solid_block_count` is the number of multi-member folders, and is `None` on a non-solid archive |
| Stream capability | `SEEKABLE` |
| Core dependencies | None — stored, LZMA, LZMA2, Delta, BCJ, BCJ2, Deflate and BZip2 read on a zero-dependency install |
| Optional | `[recommended]`: PPMd (`pyppmd`), Deflate64 (`inflate64`), Zstd (`backports.zstd`, stdlib on 3.14+), Brotli (`brotli`), LZ4 (`lz4`), AES (`cryptography`) |
| Refuses | Non-seekable sources · a signature header major version other than 0 · PPMd order outside 2–64 or memory outside 2 KiB – 4 GiB−36 (7-Zip's bounds) · LZMA1 with `lc + lp` over 4 (7-Zip writes it with `-m0=LZMA:lc=8`; liblzma cannot decode it; the same check as ZIP method 14, `decode_lzma_filter_properties`) · a coder with more than one output stream, or more than one input unless it is BCJ2 · a coder graph that is not a tree of linear chains · BCJ2 in an encoded header · external property data (names, times, attributes, start positions, comment) · alternative coder methods (`0x80` flag) · unknown coder method ids · `NumCyclesPower` 25–62 · a second encoded-header layer · writing |

The extras are named for what they provide rather than for 7z, because every one of
those codecs is shared with ZIP or TAR. See
[`packaging-and-extras`](../../openspec/specs/packaging-and-extras/spec.md).

**Three things a reader might expect and will not find.** A BCJ2 folder, which is what
7-Zip's own `-mx9` picks for an x86 executable, decodes at about half the speed of the
same file under BCJ, because its decoder is pure Python, and keeps no seek points, so a
backward seek decodes again from the folder start (§3, §5).
Nothing caches a folder decode: N random `open()` calls
into one solid folder are N decodes from the folder's start, and the only signal is
`AccessCost.SOLID` (§2.3). And 7z has no password check value at all, so on a
store-or-copy member with no digest a wrong password produces bytes rather than an
error — `DIGEST_UNVERIFIABLE` says so (§4).

## 1. Shape

Four properties generate most of this page. Everything below is a consequence of one of
them.

```
[ stub? ]  [ 32-byte signature header ]  [ packed streams … ]        [ next header ]
                 │ magic | ver | CRC                                       ▲
                 │ NextHeaderOffset ─────────────────────────────────────────┘
                 └── byte 0 for every offset in the archive

next header  ──▶  kHeader          a property tree, parsed directly
             └─▶  kEncodedHeader   a folder: decode it, then parse what comes out

property tree ──▶ MainStreamsInfo ──▶ PackInfo        pack_pos, one size per packed stream
                                      UnpackInfo      folders: coders, bind pairs, output sizes
                                      SubstreamsInfo  how each folder's output is cut up
                  FilesInfo       ──▶ names, empty-stream bits, times, attributes
```

**A folder is a decode program, not a container.** It lists coders, the bind pairs
wiring one coder's output to the next one's input, and which of the resulting inputs are
fed from the packed data. Nothing in it is a member. So the unit of decoding is the
folder and never the member; the codec chain belongs to the folder, which is why
`member.compression` is identical for every member in one folder and is built once per
folder rather than once per member; a *solid* archive is not a different structure but
the ordinary one with more than one member cut out of a folder's output; and a coder
graph is general enough to express shapes a linear pipeline cannot run. archivey accepts
a **tree of linear chains**: every coder has one output, every coder but BCJ2 has one
input, and `plan_folder` reads the graph from the one unbound output down, each input
either a pack stream or bound to one coder's output (`sevenzip_pipeline.plan_folder`).
A linear folder is the one-branch case and plans as it always did. A shape the planner
will not run (a multi-output coder, a multi-input coder other than BCJ2) is
`UnsupportedFeatureError`; a cycle, or an input that is neither packed nor bound, is
`CorruptionError` at plan time, before the password check can mistake it for a wrong
key. A graph that is not well formed at all — no
coders, a bind pair out of range or reused, an out-stream count that leaves no single
folder output, a packed index that is also bound — is `CorruptionError` at parse, in
`sevenzip_parser._read_folder`. So is a header whose declared substreams outnumber the
files that consume them, or whose folders name pack streams the PackInfo does not hold.
BCJ2 is the shape that matters in practice: it takes four inputs (`main`, `call`, `jump`,
`rc`), each its own pack stream behind its own chain. Each pack stream gets its own
`SharedSource` view, so the four chains keep their own positions, and a
`Bcj2DecoderStream` (`internal/streams/codecs/bcj2_filter.py`) joins them. Each branch is capped at its
declared size, because 7-Zip's LZMA branches carry no end marker.

The header can be a folder too. `kEncodedHeader` is a compressed, optionally encrypted
folder whose output *is* the real header, so the parser has to run the decode pipeline
before it can list anything, and a password can be needed before a single member name
exists (§2.2). Ordinary 7-Zip archives take that path — measured, an archive of nine
members written by 7-Zip 23.01 carries an encoded header while a single-member one does
not (§3).

**A member is an offset and a length into a folder's output, and neither number is
stored.** `SubstreamsInfo` gives the number of members per folder and their sizes; the
file table is matched onto those substreams *by position*, skipping every entry that has
no stream (`_map_files_to_folders`). No entry in the file table names its folder. So
reaching member *k* of a folder means decoding and discarding everything before it —
`_member_prefix` gives the sum of the earlier members' sizes and the read skips that
far. The member walk at open keeps that sum as a running total per folder, so finding
every member's offset costs one addition per member. The decode cost does not change: a
sequential pass decodes the folder once, and an `open()` of each member decodes that
member's prefix again. One wrong count in the header shifts every later member onto the
wrong bytes, which is the same demux hazard [`rar.md`](rar.md) §4 has at a subprocess
pipe, moved into the header where the attacker writes it directly; and the *last*
substream size in each folder is not stored at all but derived by subtracting the others
from the folder's declared output, so a folder whose substream sizes overrun its output
is `CorruptionError` at parse rather than a short read later.

**A member with no stream is not in the stream map at all, and there is no directory
flag.** The `kEmptyStream` bit takes an entry out of the substream mapping entirely;
`kEmptyFile` and `kAnti` then say which kind of stream-less thing it is. A directory is
what is left: empty stream, not an empty file, not an anti item
(`_file_record_from_props`). The two bits are indexed over the stream-less entries, so
each `kEmptyStream` clears them, as `7zIn.cpp` does: a bit is kept only while the
`kEmptyStream` vector it was supplied under is in force, so a crafted header that
repeats `kEmptyStream` drops it, whether the entry now has a stream or is still
stream-less (`_read_files_info`). 7-Zip 23.01 refuses a header that repeats
`kEmptyStream` (`E_INVALIDARG`), which is the evidence that no real producer writes it
(DR-5a); archivey keeps listing the recoverable members (DR-2, DR-17). So an empty file
and a directory differ by one bit in a property that may be absent; a stream-less member
has `folder_index is None` and opens as an empty stream with no decode and no password;
and a symlink is *not* one of these — its target string is its member data, so it
occupies a substream like any file. That last one is why listing is not free (§2.2).

**Every offset in the archive is measured from the signature header, not from byte 0.**
`NextHeaderOffset` and `pack_pos` are both signature-relative, so an archive that begins
part-way through a file needs no arithmetic anywhere except at the point where its origin
is found. `SevenZipReader._view` rebases once and every seek below it is unchanged, which
is what makes a self-extracting stub cost one scan rather than a special case per read
(§2.1).

## 2. The pipeline here

Each stage: who does the work, what is 7z-specific rather than general, what is refused.

### 2.1 Identify

One magic at offset 0 — `7z\xbc\xaf'\x1c` — and two extensions, `.7z` and `.cb7`. Magic
wins over the extension; the comic-book aliases are listed in [`zip.md`](zip.md) §2.1.

A candidate is confirmed by `validate_sevenzip_signature_header`
(`internal/backends/sevenzip_detect.py`) before it is reported, and 7z is the format whose
validator has the most to work with: the 20-byte StartHeader carries its own CRC, so
identity can be *proved* rather than estimated. The order matters and is 7z's own:

- Magic, then major version 0. Anything else is `NOT_THIS_FORMAT` — not this format
  rather than a damaged one, so the scan keeps looking. An archive at offset 0 is claimed
  by magic alone, so the parser (`read_signature_and_next_header`) checks the version
  again and refuses any other as `UnsupportedFeatureError`, as 7-Zip refuses it as an
  unsupported version.
- `StartHeaderCRC` over the StartHeader. Once that matches, identity has held, and every
  later objection is `DAMAGED` rather than a rejection: an oversized next header, or a
  declared end past the provable remaining length. The scan can then fall back to a
  damaged candidate when nothing valid is found, so a truncated payload behind a stub
  names its truncation instead of reporting that no 7z was there.
- `NextHeaderSize == 0` is `NOT_THIS_FORMAT` even with a valid CRC. That is an empty
  archive, and nobody ships a self-extractor with no files. A genuine empty `.7z` at
  offset 0 is claimed by magic and never reaches the validator.
- When the remaining length is unknown the CRC alone is enough. Peeking at the declared
  end would grow the prefix to the whole archive to answer a question the CRC has
  already answered.

`find_signature_offset` runs the same scan for a *forced* `format=SEVEN_Z`, with the same
validator, which is what makes opening an SFX file work with no detection involved. A
source with no 7z magic in the window fails loudly rather than opening as an empty
archive.

The cue set, the scan window, the budget tiers and the argument for validating a hit at
all are shared with ZIP and RAR —
[`topics/prefixed-archives.md`](../topics/prefixed-archives.md). What is 7z's alone: the
CRC-first ordering above, the empty-archive rule, and the fact that its parser takes a
start offset and reads in place rather than copying the payload out.

### 2.2 Open and list

**The header load is two-phase and may need a password before any member exists.** Read
the signature header, verify both CRCs, read the next header, parse it. If what comes
back is a `kEncodedHeader`, decode its one folder through the ordinary folder pipeline
(§2.3) and parse the result. Exactly one layer is unwrapped: 7-Zip writes one, and a
second is hostile — a COPY-coded encoded header whose packed bytes are itself decodes to
itself for ever ([`threat-model.md`](../threat-model.md) O14). As in 7-Zip, the encoded
header must have exactly one folder and must decode to a `kHeader`; anything else
(nothing, a bare `kEnd`, a header split over two folders) is `CorruptionError`, not an
empty archive. `load_sevenzip_archive` in `sevenzip_reader.py` is the only
implementation of this flow; the reader and the fuzz harnesses both call it.

Two things in that path are 7z-specific rather than general:

- **A wrong password on an encrypted header does not fail cleanly.** There is no check
  value, so the wrong key yields garbage that LZMA usually refuses — but not always.
  A decoded header that parses to zero file records is treated as a rejected password,
  never as an empty listing, because no legitimate writer encrypts an empty header
  (O8, measured at ~0.3% of writes without the rule).
- **The listing bound fires at parse, before the table is allocated.** Every count the
  header claims — files, unpack streams per folder, and their running total — is checked
  against the header's own byte length first (a count cannot exceed the bytes that must
  describe it) and then against `listing_limits.max_members`, which `ListingLimits.UNLIMITED`
  removes. The byte check is on the *decoded* header, so it binds less than it looks:
  header compression shrinks a uniform table to almost nothing: a 315-byte file
  declaring 1 000 000 directory entries would cost about 858 MB and 16 s at open with
  the cap lifted. That measurement is why davitf lowered the default from 1,048,576 to
  262,144 on 2026-10-07, replacing the 2026-10-01 decision to accept it; the default
  now refuses that file at open, and the same header shape costs about a quarter of
  that at the cap ([`design-rules.md`](../design-rules.md) DR-9, which reopens it if a
  measured real archive class hits the default).
  The per-folder coder-graph cap is a different number and must not be reused
  here: a solid archive's unpack-stream count *is* its member count, so capping it at
  65 536 refused ordinary 7-Zip output (O13). That cap is now 7-Zip's own, refused as
  `UnsupportedFeatureError`: at 65 536 a small header drove the planner and the nested
  decode streams into `RecursionError`. 7-Zip 26.03 defines `k_Scan_NumCoders_MAX` and
  `k_Scan_NumCodersStreams_in_Folder_MAX`, both 64, in `CPP/7zip/Archive/7z/7zIn.cpp`
  (`CInArchive::ReadUnpackInfo`; `ReadUnpackInfo` in `C/7zArcIn.c` has the same rule).
  It allows 1 to 64 coders per folder and at most 64 in-streams per folder, counted as
  a running total over its coders, and it requires exactly one out-stream per coder.
  The parser applies the same in-stream caps and caps out-streams at 64; the reader
  refuses a multi-output coder when the member is opened. 7-Zip calls a folder with 0
  coders unsupported; archivey keeps `CorruptionError` for it, because an empty graph
  cannot be a valid folder.

**Once the header has parsed, the open reads up to 1 MiB past the archive's end.** The
end is the later of the next header's end and the last packed stream's end (an encoded
header's packed stream included). A non-zero byte in that window is
`ARCHIVE_TRAILING_DATA` (DR-3); zeros are silent. It runs after the header so a wrong
header password or a damaged header is reported as that. The scan is the shared
`internal/trailing_scan.py`, which the RAR and ISO readers are meant to share.

**Member metadata comes out of the file table, the substream mapping and the folder in
three different places.** Names are UTF-16LE with no encoding flag and no ambiguity, so
`encoding=` is dropped with the shared `ENCODING_ARGUMENT_UNUSED` diagnostic and
`raw_name` keeps the UTF-16LE bytes. Backslashes in a stored name are separators. The
decode uses `surrogatepass`, because NTFS lets a name hold a surrogate without its
partner and 7-Zip lists such a name: the unit stays in `name`. Under `STRICT` and
`STANDARD` the O7 portable-name rule escapes its UTF-8 bytes (`hi%ED%A0%80`, on every
OS). Under `TRUSTED` extraction writes it as 7-Zip 23.01 does on Linux (U+D800 as
`ed a0 80`, measured with the container's `7z`) or as the exact name on Windows
(`filters.disk_spelling`). A unit in U+DC80–U+DCFF keeps the library-wide
`surrogateescape` meaning and is written as one byte, where 7-Zip writes three (§5).
The archive comment decodes with `surrogatepass` too, so a lone unit there no longer
refuses the archive; an odd byte count is still a `CorruptionError`. Timestamps are
Windows FILETIME, and an out-of-range value degrades to a diagnostic rather than an
error. The diagnostic's `field` is the member attribute the slot would have filled, so an
unreadable "Created" is reported as `created` or `ctime` by the host rule below.
`attributes` is the Windows attribute word, with a Unix mode in its high 16 bits when
the writer put one there — which is also how member type is decided: `S_ISLNK` or the
reparse-point bit makes a symlink, `S_ISDIR` or a stream-less non-empty entry makes a
directory, and a FIFO, device or socket mode makes `OTHER` only on a stream-less entry
(what 7-Zip and p7zip write); a special mode on an entry that owns a stream is a `FILE`
reporting `MEMBER_SPECIAL_FILE_HAS_DATA` (7-Zip's own reader sets `IsDir=false` for any
entry with a stream and extracts the bytes), DR-25. Both carry
`extra["special_file_type"]`, and so does a directory or reparse-point entry whose high
word names a special file: the key records the mode, the type the structure. A member
with a data stream is never a directory, whatever its mode says, as in 7-Zip, which
lists `drwxr-xr-x` with the data's size and extracts a regular file: its data is read
and extracted as a file's. Nor is it an anti item: a stale `kAnti` bit cannot reach it
(§1, "A member with no stream"). That second shape is one 7-Zip refuses outright, so
there the file typing follows DR-2 and DR-17, and the clearing is what 7-Zip would do if
it got that far. A reparse-point symlink's target is read from its reparse data and
normalized as ZIP's is ([`zip.md`](zip.md) §2.2.1): `\??\C:\Windows` lists as
`C:/Windows`, and extraction refuses a drive or UNC target on every OS. The same word
decides what "Created" means. 7-Zip on Linux and p7zip fill it from `st_ctime`, set the
Unix-extension bit (`0x8000`) and put `st_mode` in the high word; the time then goes to
`ctime` and `created` stays `None`.
The word holds a Unix mode when the high word has a Unix file type (`S_IFMT` bits), not
on the bit or a non-zero high word: `0x8000` is also Windows `INTEGRITY_STREAM`, and
Windows attributes such as `PINNED` (`0x80000`) sit above `0xFFFF`. 7-Zip 23.01 applies
the same test: `0xa1ff0020` lists as `lrwxrwxrwx` and extracts a symlink, `0x01ff8020`
lists no Unix mode. Measured on a symlink stored by `7z a -snl -mhc=off` (an unencoded
header), with the attribute word patched in the next header, the next-header CRC (start
header offset 28) and the start-header CRC (offset 8, over bytes 12–32) recomputed, and
the word read back from the `Attributes` line of `7z l -slt`. One Windows attribute,
`STRICTLY_SEQUENTIAL` (`0x20000000`), puts `S_IFCHR` there, and 7-Zip lists such a file
as `c---------`; archivey counts a special file type only with the bit, so that file
stays an extractable `FILE` with no mode. `mode`, the type, the special type,
`create_system` and this slot all use that one test (`_unix_mode`). 7-Zip on Windows
sets none of it (attributes `0x20`) and stores the birth time. 7-Zip, p7zip and
libarchive on Linux and macOS all store `st_ctime`. libarchive on Windows puts a Unix
mode in the high word and stores the birth time, which therefore lands in `ctime`.
Per-writer measurements:
[`writer-timestamp-slots.md`](../investigations/writer-timestamp-slots.md).
`compressed_size` is the folder's packed size, repeated for every member in it, because
the format has no per-member packed size to give. A member with no name at all takes the
archive's stem.

**Listing a solid archive that contains a symlink decodes that whole folder.** The link
target is member data, and the shared listing pass resolves every link's target as soon
as it sees one (`base_reader._resolve`). In a non-solid archive that is one small folder;
in a solid one it is the folder the link happens to sit in, which is usually the whole
archive. Measured on a six-member solid archive whose symlink is the last substream:
listing decoded all 135 101 bytes, and the same archive written with `-ms=off` decoded 6.
`ListingCost.INDEXED` does not express this, and an encrypted folder is the one case it
stays quiet — the shared link-target read (`BaseArchiveReader._link_target_from_data`)
catches `EncryptionError` and reports it, so listing does not demand a password.
`ArchiveyConfig.read_link_targets=False` turns this off: listing and a pass decode
nothing for link targets, and a target stays unset until the caller reads the link
(`extract_all()`, `open()`) and it is read then; until that read the link reads
`member_state_final=False`. Under the default `True`, a
`stream_members()` pass without a prior listing reads each link's bytes through its own
folder decoder as it passes the link, in either access mode, and sets every target when
it reaches the end, so the folder is not decoded a second time for them. One case is
decided at the link instead of at the end: a member flagged as a reparse point whose
bytes are not a link buffer. It is re-typed to a file there, as listing would re-type it
(a directory-shaped entry stays a link with no target), and the pass yields it with its
whole content: the bytes already read, then the rest from the same decoder
(`SevenZipReader._capture_link_data`). Deciding at the end yielded it as a link with no
stream and lost the content, since the decoder cannot go back. A pass abandoned early
keeps the bytes it read without setting the targets; a later listing uses them and
decodes the folder again only for the links the pass did not reach (from the folder
start, since a solid decode cannot resume). That cost is per pass: each abandoned pass
that reaches a link no earlier pass reached pays the folder's prefix again.

So `member_state_final=False` covers two things here: a link whose target is unread
(the read sets the target, or makes a reparse point whose data is no link buffer a
file), and, during a pass with no listing call before it, `is_current` and
`link_target_member`, which the end of the pass settles. The header gives every other
field before a member is yielded, unlike a ZIP read from a pipe ([`zip.md`](zip.md)
§2.2.2).

**Split sets are joined before the reader sees them.** 7-Zip's `-v` writes `name.7z.001`,
`name.7z.002` … as raw byte slices of one finished archive, so the parts are concatenated
and the archive is parsed across the join; opening any part opens the set. The discovery
and joining code is shared with ZIP and is described in [`zip.md`](zip.md) §2.2 — what is
7z's is only that `ArchiveInfo.extra["7z.volume_count"]` reports how many parts were
joined, and that `is_multivolume` follows it.

### 2.3 Member data

Opening a member is opening its folder and slicing the output. The folder decode is
planned first and executed second: `plan_folder` resolves the coder chain into an ordered
list of stages while opening nothing, then `open_folder_pipeline` folds each stage onto
the packed slice. Keeping the branchy staging decisions in a pure function is what makes
them testable without archives.

The staging rules are the 7z-specific part, and each one exists because a combined chain
was measured returning wrong bytes:

- **LZMA2, with the Delta or BCJ filters decoded after it, is one raw liblzma chain.**
  Decode order is outer-first and liblzma wants encode order, so the filter list is
  reversed. The chain must end, in encode order, in its one LZMA1/LZMA2 filter, and hold
  at most four filters. So a filter decoded *before* the codec (`-m0=LZMA2 -m1=BCJ`
  stores that order) is its own stage, and so is each further LZMA1/LZMA2 coder; an
  audit found both refused as unsupported when they were folded into one chain.
- **A coder that decodes past its declared size is `CorruptionError`,** as 7-Zip reports
  a data error. This covers every codec that ends its own stream: an LZMA2 chain, Deflate,
  Deflate64, BZip2, Zstd, LZ4 and Brotli. LZMA1 and PPMd stop at the declared size
  themselves and check their input there (*Input after the stream*, below); the check
  wraps them too, since its read past the size is where they report it. Every reader
  above the codec stops at the
  declared size (the member slice, a BCJ2 branch slice, a Delta or BCJ filter after the
  codec), so the surplus was invisible. `_DecodedPastSizeCheck` wraps the codec's output
  and, when that output reaches the declared size, asks the decoder for one more byte of
  output. That is not a second decode, but it is not one read of input either: the
  decoder reads as much of the coder's packed input as it needs to produce that byte, so
  a tail of streams that decode to nothing is read to its end. The cost stays linear in
  the archive, the same bound as decoding the folder, so it is accepted rather than
  bounded. How the edge cases come out:
  - *AES padding before the codec.* The AES stage decrypts whole 16-byte blocks, so the
    codec's input ends in up to 15 pad bytes. The check counts the codec's *output*, not
    its input, so the pad is never surplus. Every codec stage's input is cut at its
    `pack_size` (the AES coder's unpack size), so the pad is not in it, and the input
    check below never sees it. A decoder error on the probe byte is not surplus either,
    except `DataAfterEndError`, input left after the stream (below).
  - *Input after the stream.* A coder's data is one stream, as 7-Zip reads it, and its
    input ends with that stream (7-Zip 23.01 `7z t` fails any byte left: "Data Error"
    for LZMA, LZMA2 and PPMd, "There are some data after the end of the payload data"
    for Deflate, Deflate64 and BZip2). archivey opens every coder with
    `StreamConfig.refuse_input_after_end`, so a byte the codec leaves, a zero byte too, and a second
    stream raise `DataAfterEndError` (a `CorruptionError`), after the output before
    them has been read, whatever the declared size and CRC cover (the bytes may be a
    side channel: `design-rules.md` DR-3). rapidgzip on a Deflate coder is the one
    exception: its end check decodes only the tail after the last point of rapidgzip's
    index, so a second stream that holds that point, with an unpack size and CRC that cover both,
    reads as both, as the ZIP handbook (§2.3) describes for a DEFLATE member.
    - LZMA1 and PPMd have no end marker in 7z by default, so they stop at the declared
      size, and their input must end there too. LZMA1 (`_LzmaToSizeDecoder`) holds the
      last two input bytes back from liblzma to see which byte completes the output,
      then reads whether the range coder ended there by feeding zeros after it: from a
      zero code liblzma decodes only zero bytes. One zero byte past that point reads,
      since 7-Zip's encoder sometimes flushes it (7-Zip's decoder reads that byte when
      its range is below 2^24 at the end, which liblzma does not expose). So archivey
      reads a zero byte added after a stream that 7-Zip refuses: on 40 7-Zip-written ZIP
      LZMA members, 7-Zip 23.01 refused one added zero byte on all 40 and archivey on
      the 2 that already ended in 7-Zip's flush byte. Two zero bytes are refused, as by
      7-Zip; a marker right at the size is checked
      like an LZMA2 one. With a Delta coder after LZMA1 in the same liblzma chain,
      the zeros decode to copies of the last `dist` output bytes rather than to
      zeros, and the check compares against those (libarchive's
      `test_read_format_7zip_delta_lzma1.7z` was refused before). PPMd7 must reach pyppmd's `eof` (its range code at zero) with
      no `unused_data`. A declared size short of the data ("cut") is therefore
      `CorruptionError`, not `TruncatedError`: the input is too long, not short. Not
      seen: a cut that hides only zero bytes of LZMA1 data (the code stays zero), and a
      cut of PPMd's last few symbols after pyppmd's sticky `eof` rose early.
    - The exception: the Zstd and LZ4 decoders read concatenated frames as one
      stream, so a second frame is not input after the stream. Their output counts
      together: a second frame is data when the declared size includes it and
      surplus when the size stops before it. A ZIP Zstd member reads the same way
      (maintainer, 2026-10-21). Bytes after the last frame that start no frame are
      refused.
  - *Accelerators.* rapidgzip reads on past the first stream. At the bytes after a
    BZip2 coder's stream it hands the read over to the standard library, which refuses
    them, so the verdict is the same with the accelerator off. A Deflate coder gets the
    same verdict for junk, zeros and a cut stream; a second Deflate stream that holds
    the last point of rapidgzip's index reads as content (above, and DR-5a). zlib
    parses only the tail after that point, so the output before it is rapidgzip's
    alone. A folder's CRC checks it, but a folder with no CRC (O12) has no independent
    check of that stretch beyond the accelerator fuzz targets, which compare rapidgzip
    with zlib. The decode from the start stays off there too: it would bring back the
    cost the tail check removes (maintainer, 2026-10-25).
  - *Under AES, the password check can meet it first.* When the check decodes the whole
    folder, as it does for one inside its 64 KiB prefix, it reports the folder as "wrong
    password or corrupt", as it does for any damage it decodes; the surplus
    `CorruptionError` is in the cause chain. Whether it decodes a larger folder whole
    depends on the codec: it walks to the member CRC when the codec cannot reject a
    wrong key by itself, as Brotli cannot.

- **Every coder is held to its own declared size, not only the folder's output coder.**
  COPY, Delta and BCJ output exactly as many bytes as they read, so the planner refuses
  one whose size differs from its input coder's (`CorruptionError`). That is what makes
  the chain checks above cover the codec: inside a liblzma chain only the last filter's
  output is visible, and it equals the LZMA1/LZMA2 coder's size. A COPY coder over a pack
  stream, whose size the folder does not carry, has its output checked by
  `_DecodedPastSizeCheck`, so pack bytes past its size do not reach the next coder.
  7-Zip reports each of these as a data error.
- **LZMA1 plus BCJ is never one chain.** In a single raw chain liblzma silently drops the
  branch filter's trailing partial block, which it releases only on `LZMA_FINISH` — and
  without an end-of-stream marker, which the 7-Zip CLI usually omits, it never learns the
  stream ended. Measured: 20 of 24 CLI-written archives came back short by 1 to 15 bytes,
  with a correct prefix and no error raised, identically on CPython 3.10 through 3.14. So
  each LZMA1 run is staged on its own, capped to its declared output size so it cannot
  over-read into the next stage, and each BCJ runs above it. The CPython fix usually cited
  for BPO-21872 addresses `FORMAT_ALONE` incremental reads, which is a different path, so
  "that bug is fixed now" does not apply — the measurement and that caveat are recorded
  next to the staging rule in [`library-analysis.md`](../library-analysis.md). Every
  LZMA1 chain is capped, with or without a BCJ above it, since a following coder reads
  in blocks too.
- **BCJ or Delta with no LZMA1/LZMA2 in the run** — after COPY, or after Deflate — is
  one stage per filter, over its own LZMA2 framing. liblzma's raw format needs a chain to
  end in LZMA1 or LZMA2, so a filter-only run can never be one chain; before this rule a
  Delta-only folder, which 7-Zip writes and reads, was planned as LZMA2 and failed as
  corrupt.
- **A BCJ coder's 4-byte property is its start offset** and is passed to liblzma as
  `start_offset`, in a chain or in its own stage. Writers almost always omit it or write
  zero; an offset the filter's alignment forbids (ARM needs 4, IA64 16, RISC-V 2) is
  refused at plan time.
- **ARM64 (`0x0A`) is never in a liblzma chain.** 7-Zip 23 writes it by default for
  AArch64 executables (`ARM64 LZMA2`), and `7z a -m0=ARM64:4096` writes a start offset.
  Python's `lzma` refuses filter id 10 in a raw chain, so ARM64 runs as its own stage in
  pure Python (`internal/streams/codecs/arm64_filter.py`, liblzma's `arm64_code`), and so does every
  filter decoded after it in its run. A start offset that is not a multiple of 4 is
  refused at plan time, as 7-Zip refuses it. The filter decodes real AArch64 code at
  about 350 MB/s; a 7z read of an ARM64+LZMA2 folder ran at about 45 MB/s against 55
  without the filter. The `.xz` ARM64 filter does not go through this path: liblzma 5.4
  and later decodes it inside the xz stream.
- **RISC-V (`0x0B`) is never in a liblzma chain either.** 7-Zip 24 added it (`7z a
  -m0=RISCV:<n>` writes a start offset; 7-Zip 26.05 did not pick it by itself for a Go
  RISC-V executable). It runs as its own stage in pure Python
  (`internal/streams/codecs/riscv_filter.py`, liblzma's `riscv_decode`), on the same
  `PythonBranchFilterDecoder` as ARM64. Its instructions are 2-byte aligned, so an odd
  start offset is refused at plan time, as 7-Zip refuses it. A converted instruction
  needs up to 8 bytes, so up to 7 bytes wait for the next input. The filter decodes a Go
  RISC-V executable at about 75 MB/s; a 7z read of a RISCV+LZMA2 folder ran at about 33
  MB/s against 71 without the filter. Hostile input where every 4-byte word is a JAL
  decodes at about 5 MB/s. An `.xz` stream with the RISC-V filter needs liblzma 5.6
  or later; an older one is refused as unsupported.
- **Everything self-contained** (Deflate, Deflate64, BZip2, Zstd, Brotli, LZ4, PPMd) is
  one stage, handed both its declared output length and its input length. PPMd7 has no
  end mark and needs the first; the accelerated Deflate path needs the second so AES pad
  bytes are not mistaken for a concatenated member.
- **BCJ2** is the source of its chain: four branch chains, each planned by the rules
  above with its own coder indices, feed a pure-Python decoder. It keeps no seek
  points: `open()` on a later member decodes from the folder start, and with
  `seekable=True` every branch is opened seekable so a backward seek rewinds all four
  inputs and decodes again. The decoder refuses an input that ends early
  (`TruncatedError` naming the stream) and a byte left in `main`, `call` or `jump` after
  the output (`CorruptionError`, after reading at most one byte, never draining). It does
  not check `rc`: 7-Zip 23.01 left one unused `rc` byte on `python3.11` at `-mx9`, so a
  strict check would refuse good archives. The encoded header stays linear-only; no
  writer puts BCJ2 there.

Branch filters other than ARM64 and RISC-V decode through liblzma rather than `pybcj`,
which is no longer imported (and has neither of those filters):
`pybcj` unpacks its size as a signed 32-bit int, and its IA64 filter drops the trailing
partial block. Both are real-user bugs on ordinary archives, both are open upstream, and
both are written up, with the measurements, in
[`pybcj-upstream-report.md`](../investigations/pybcj-upstream-report.md).

**AES is a coder like any other, and it is the first stage.** The 7z KDF is
SHA-256 over `salt + password + counter`, repeated `2**NumCyclesPower` times, with the
password encoded UTF-16LE. `NumCyclesPower` is attacker-chosen, so values 25–62 are
refused outright, matching 7-Zip's own decoder clamp; `0x3f` is the documented no-hash
sentinel and is honoured. Derived keys are cached per reader by `(password, salt,
cycles)`, which matters because a multi-folder encrypted archive re-derives otherwise.

**Confirming a password means decoding, because there is nothing else to check.** With no
verifier bytes, a candidate is judged by decoding and comparing CRCs, in 64 KiB chunks so
peak memory is one chunk. The decode follows a plan from the shared confirmation ladder
(`internal/password_confirm.py`), whose rungs are, strongest first:

1. *A cheap key check* — an O(1) test on the key. 7z's format has none; ZIP's check byte
   and `pw_verify` sit here. `sevenzip-aes-tail-key-check` proposes one for 7z from the
   AES padding at the end of the packed stream.
2. *The earliest integrity anchor.* Member CRCs in substream order, then the folder
   digest, which only ever wins when no member CRC is reached first. The plan stops once
   CRC-verified bytes reach 4, because fewer carry less than 32 bits. So a solid folder's
   first member usually decides, and the correct password no longer pays a folder decode
   before its member is served.
3. *Codec rejection.* A chain holding a decoder measured to fail on random input — which
   is what a wrong AES key feeds it — never walks a CRC past 64 KiB of plaintext: the
   decoder settles a wrong key inside that prefix. A survivor is *inconclusive*, not
   confirmed. Rejecting: LZMA1, LZMA2, BZip2, Deflate, Deflate64, Zstandard, LZ4.
   Non-rejecting: Copy, PPMd, Brotli (about one random input in twenty decodes a full
   prefix), and every filter — Delta and BCJ are bijections, which is why
   `MethodKind.LZMA_FAMILY` is the wrong predicate. A bounded plan also caps the packed
   input at 1 MiB, the inner-TAR probe's bound, since bzip2 consumes a whole block before
   emitting.

A non-rejecting chain still walks to its CRC however far it is, because nothing else can
tell a wrong key there; that walk, repeated per candidate, is the residual of threat-model
O12. A folder with no CRC at all is decoded to the prefix and no further. An inconclusive
password is accepted but kept out of known-good while another candidate could still be
the right one. A member stream from its folder that has returned some bytes and is
then closed before EOF, or that jumped past its read position and so gave up its CRC
(a forward seek in a compressed folder keeps it: the next read decodes the gap), emits
`ENCRYPTED_MEMBER_UNVERIFIED` on close (`reason` is `partial_read` or `seek`).
`ExtractionLimits` do not reach this path.

**The confirm cannot tell damage from a wrong key.** A CRC mismatch or a decoder error
inside the stretch the confirm decodes rejects the candidate, so an encrypted folder
damaged there raises `EncryptionError` ("Wrong password or corrupt 7z folder") with the
right password too. That stretch runs to the earliest CRC when it lies within 64 KiB of
plaintext or the chain rejects nothing, and to the 64 KiB prefix otherwise. Damage past
it is found by the member read, as `CorruptionError` from its CRC or its decoder. A
store-or-copy member with no member CRC and no folder digest has nothing to find it, and
returns the damaged bytes (§4). The read remaps nothing either way, so a wrong key
that survived the confirm would also surface there as `CorruptionError`, where ZIP names
both causes; the confirm makes that rare, since a rejecting chain settles a wrong key
inside the prefix and a non-rejecting one walks to its CRC. Three failures
are deliberately *not* remapped to a wrong password —
an unsupported `NumCyclesPower`, a missing `cryptography`, and an AES-CBC mid-block
truncation — because candidate iteration advances on `EncryptionError` and would otherwise
walk the whole password list over a structural problem.

**Sequential and random access are different code paths with different costs.**
`stream_members()` opens each folder once and hands out member views over a
`SolidBlockReader`, so a whole-archive pass decodes each folder exactly once, and a folder
none of whose members are read is never decoded and never asks for a password. Random
`open()` opens the folder again, from the start, and skips the prefix — so reading *k*
members of one solid folder out of order costs *k* decodes, each from the folder's
beginning. Nothing caches the result. When `seekable_members=True` and the chain supports
it, the slice seeks instead of skipping; otherwise it skips forward.

### 2.4 Extract

Nothing here is 7z-specific. Path safety, link handling, collisions and limits are the
shared extraction machinery ([`safe-extraction`](../../openspec/specs/safe-extraction/spec.md)),
and member digests are verified by the same wrapper every backend uses.

One format-specific member kind reaches it: an **anti item** is a tombstone written by an
incremental update to say a file was deleted since the previous archive. archivey lists it
as `MemberType.ANTI`, refuses to read it as data, marks the earlier member of the same
name superseded, and writes nothing for it.

**What it does delete is bounded to this run's own writes.** `_apply_anti_item`
(`internal/extraction.py`) removes the destination when — and only when — this same
`extract_all()` call already wrote that path: it `rmdir`s a directory or `unlink`s a file
and releases the collision claim, so the run does not end advertising content that is
gone. A path this run did not write is left alone and the result is `EXTRACTED` with the
filesystem untouched. The bound is the write, not the file's history: `_dispatch_write`
adds a FILE, SYMLINK or HARDLINK destination to that set on any `EXTRACTED`, and only the
DIRECTORY branch checks `os.path.lexists` first. So a file that was already on disk and
that this run overwrote is in the set, and a later tombstone for it does delete it — what
goes is the content this run put there. That is the departure from what the format asks
for, and it is the deliberate half (§6). No test reaches the delete branch — the tests
cover the leave-alone side — which is a gap rather than a claim.

### 2.5 Write

Not shipped, for any format. `py7zr` is a development oracle only — it writes fixtures
and cross-checks listings and bytes in the tests, and it is not on
the read path.

## 3. In the wild

**7-Zip picks BCJ2 at its top level and only there.** Measured on 7-Zip 23.01 against one
x86-64 ELF binary:

| Level | Coders 7-Zip wrote | archivey |
| --- | --- | --- |
| `-mx1`, `-mx3`, `-mx5`, `-mx7` | `LZMA2 BCJ` | reads |
| `-mx9` | `BCJ2 LZMA2 LZMA LZMA` | reads (pure-Python BCJ2 stage) |

So BCJ2 is not an exotic corner: it is what the reference tool produces when someone asks
for maximum compression on executables. 7-Zip takes the execute bit into account on Linux:
the same ELF bytes got BCJ2 at mode 0755 and plain LZMA2 at 0644. Non-executable content is
unaffected at every level. libarchive's nine `test_read_format_7zip_bcj2_*` fixtures,
written by an older 7-Zip with BCJ2 over stored, LZMA, LZMA2, Deflate and BZip2 branches,
read and match `7z x`.

**Ordinary archives carry a compressed header.** Measured on the same 7-Zip: a nine-member
archive written at the default level came back with a `kEncodedHeader`, while the
single-member archives above carried a plain one at every level from `-mx1` to `-mx9`. So
the encoded-header path is the ordinary one rather than the exception, which is why the
parser has to be able to run a decode pipeline before it can list a single name.

**py7zr differs in two ways that matter to us.** It does not write the folder CRC on the
encoded header, so header-encrypted archives it produces lose the deterministic
wrong-password check that reference 7-Zip archives have (O8) — and since our own test
fixtures are written through py7zr, they share that gap. Its branch-filter lists omit
IA64, so LZMA1+IA64 goes through a combined chain and hangs at 100% CPU; archivey reads
all six branch filters. Both are written up in
[`investigations/py7zr-upstream-report.md`](../investigations/py7zr-upstream-report.md).

**Zstd, Brotli and LZ4 ids come from the 7-Zip ZS fork**, not from upstream 7-Zip, which
supports none of them. The LZ4 fixture in `tests/fixtures/sevenzip/` is py7zr's, and
neither stock 7-Zip nor py7zr can extract it; archivey decodes it through the shared LZ4
codec.

**Self-extracting 7z archives cost the producer nothing**, because the format's offsets
are signature-relative (§1) — a stub and a `.7z` concatenated is a working archive.
`7z a -sfx7zCon.sfx` writes one, and the stub shapes seen in the wild (ELF, PE, and Mach-O
both thin and fat) are surveyed in
[`topics/prefixed-archives.md`](../topics/prefixed-archives.md) §1.

## 4. Threat surface

7z-specific only. General extraction and name hazards are §2.4.

- **The header is a compressed program that runs before anything is validated.** Listing
  an archive means decoding a folder whose coder chain, output size and pack offsets the
  attacker wrote. The bounds are: a 64 MiB cap on the next header's declared size, a
  bound on the next-header offset before the seek so a multi-EiB value cannot overflow a
  C `ssize_t`, and the same 64 MiB cap on the encoded-header folder's declared output,
  checked before decoding. An encoded header with more than one folder is refused, so
  folders cannot concatenate past that cap ([`threat-model.md`](../threat-model.md)
  O14).
- **Counts in the header are allocation instructions.** `kNumUnPackStream` with no
  `kSize` or `kCRC` following it allocates one list entry per claimed stream with no
  bytes read per stream, so no remaining-bytes check can catch it; the `all_defined`
  CRC path is the same bomb one property earlier. Bounded by header size first and
  `max_members` second, at parse (O1, O13). The names and comment the parsed header
  holds are then weighed against `max_metadata_bytes` at open (`_check_header_metadata`
  in `sevenzip_reader`); the header's own 64 MiB bound is a fixed parser limit, not
  that budget.
- **A wrong password can be undetectable, by design of the format.** 7z has no password
  check value, unlike RAR5's `pswcheck` or WinZip AES's verifier bytes. On a
  store-or-copy member in a folder with no digest and no member CRC, a wrong key
  produces bytes and there is nothing to contradict them; archivey emits
  `DIGEST_UNVERIFIABLE` with `reason="no_integrity_anchor"` rather than implying the
  decryption was authenticated. Header encryption has the related failure — garbage that
  happens to parse as an empty header — closed by treating zero file records as a
  rejected password (O8).
- **The KDF cost is in the archive, not in our config.** `NumCyclesPower` is a
  header field, so the archive chooses how much work a password attempt costs.
  Capping it at 24 matches 7-Zip and bounds a single derivation; the total across an
  archive that salts per folder is `DecoderLimits.max_key_derivation_rounds`, counted in
  summed declared rounds per cache miss (threat-model O18).
- **The substream demux is positional and unauthenticated.** Nothing in the file table
  names its folder, so a crafted substream count or size shifts every later member onto
  the wrong bytes (§1). Per-member CRCs are the backstop where the writer stored them,
  which turns a desync into a digest failure rather than silent wrong data — but they are
  optional, and an encrypted store-or-copy folder is exactly the case that has neither.
- **A name is UTF-16LE with no length prefix**, terminated by a NUL and bounded at 65 536
  code units per name; the whole blob is decoded in one call rather than per character,
  which is also what keeps a name bomb from being a CPU bomb.

## 5. Sharp edges

*Where it lives*: **format** — inherent, no implementation fixes it · **library** — an
upstream library's behaviour, fixable only there or by replacing it · **archivey** — ours.

| What you see | Where it lives | More |
| --- | --- | --- |
| An executable member 7-Zip wrote at `-mx9` reads at about half the speed of the same file under `-mf=BCJ` | **archivey** | BCJ2 decodes in pure Python: about 26 MB/s for the BCJ2 stage on `git`, 15 MB/s for the whole folder, against 33 MB/s for BCJ through liblzma (CPython 3.11). A `main` stream made of nothing but branch opcodes drops the stage to about 1.8 MB/s; `ExtractionLimits` bound extraction, and `open()` to the end is unbounded as for any codec |
| Three LZMA dictionaries are live at once for a BCJ2 folder | **format** | One per branch (`LZMA2:22` plus two `LZMA:20` for `git`), each declared by the archive. `DecoderLimits.max_decoder_memory` bounds their sum, with any PPMd branch's memory and zstd window, before a branch is built |
| Listing an archive is not free when it contains a symlink | **format** / **archivey** | The target is member data, and in a solid folder that means decoding the folder to read a few bytes (§2.2). Inherent to where 7z puts link targets; that we resolve every target eagerly at listing is ours |
| Reading members of a solid archive out of order decodes the folder once per member | **format** / **archivey** | There are no per-member entry points to resume from (§1), and nothing caches a decode (§2.3). `AccessCost.SOLID` and `solid_block_count` are the signal. A sequential `stream_members()` pass decodes each folder once |
| A wrong password returns data instead of an error | **format** | No password check value exists in 7z. With a folder digest or a member CRC the CRC catches it; a store-or-copy member with neither cannot be checked, and `DIGEST_UNVERIFIABLE` is emitted at listing so the caller knows before reading (§4) |
| A damaged encrypted member raises `EncryptionError`, as a wrong password would | **format** | No check value, so the confirm judges a password by decoding, and damage in what it decodes looks like a wrong key (§2.3). The error names both causes. Damage the confirm does not reach raises `CorruptionError` from the read, where a CRC or the decoder can see it |
| Trying a list of passwords against a big encrypted store-or-copy folder whose only CRC is at its end reads the folder per candidate | **format** / **archivey** | Nothing rejects a wrong key early on stored data, so confirmation walks to that CRC (§2.3). Peak memory is one 64 KiB chunk, not the folder. `ExtractionLimits` do not apply. Prefer one known password there |
| A 7z on a pipe or socket cannot be opened at all, in either access mode | **format** | The next header is at the end and every offset is absolute; nothing is buffered for you (ADR [0010](../decisions/0010-no-silent-buffer-nonseekable.md)) |
| An anti item removes only a path *this same run wrote* | **archivey** | It is listed, marked as superseding the earlier member of that name, and writes nothing. Deleting what the run itself wrote keeps the run's own results honest; honouring the tombstone against a path the run never touched would mean deleting a file the archive never wrote. A pre-existing file this run overwrote counts as written, so it is not protected (§2.4, §6) |
| A CRC-valid 7z signature earlier in a stub whose declared end falls short of the file is opened only when no later hit ends exactly at EOF | **archivey** | The SFX scan grades such a hit `VALID_SHORT` and keeps looking for a hit whose declared end matches the source length; the first `VALID_SHORT` hit is the fallback. Trailing bytes after a real payload (a code signature, for one) do not make the hit a decoy, so detection never rejects a short hit outright. Once open, the listing still does not cover those bytes, so they are reported as `ARCHIVE_TRAILING_DATA` like any bytes after a 7z archive's end, and `STRICT` refuses a signed self-extractor. See [`topics/prefixed-archives.md`](../topics/prefixed-archives.md) |
| A name with a lone UTF-16 surrogate extracts as `hi%ED%A0%80` under `STRICT`/`STANDARD`; 7-Zip writes `hi` + `ed a0 80` | **archivey** | The default policies write portable names, and a lone surrogate is not one: APFS refuses its bytes and no other OS spells it the same. `TRUSTED` writes 7-Zip's bytes. Maintainer decision on PR #564 |
| A lone UTF-16 unit in U+DC80–U+DCFF extracts as one byte under `TRUSTED` (`%80` under `STRICT`/`STANDARD`); 7-Zip writes `ed b2 80` | **archivey** | In a `str` that range also means a `surrogateescape` byte, and every other format, the O7 portable-name rule and `os.fsencode` read it that way. Telling a 7z unit apart would need provenance on the name. `raw_name` keeps the unit. Every other lone surrogate matches 7-Zip under `TRUSTED` |
| An empty file stored from ReFS with `INTEGRITY_STREAM \| STRICTLY_SEQUENTIAL` (attributes `0x20008000`, or `0x20008020` with ARCHIVE) lists as an `OTHER` char device with mode `0`, and extraction refuses it | **format** | `0x8000` is both the Unix-extension bit and `INTEGRITY_STREAM`, and `0x2000` in the high word is `S_IFCHR`, so the word is exactly a Unix char device with no permission bits. Nothing tells the two apart, and 7-Zip lists it as a device too. Without `0x8000` the word is a `FILE` with no mode (§2.2) |
| `encoding=` is accepted and has no effect | **archivey** | 7z names are UTF-16LE with nothing to guess. Dropped with an `ENCODING_ARGUMENT_UNUSED` diagnostic rather than silently — shared behaviour, not 7z's own |
| Reading a member from a folder 7-Zip wrote with `-m0=LZMA:lc=8` (any LZMA1 `lc + lp` over 4) raises `UnsupportedFeatureError`, though 7-Zip reads it. Listing does not raise: a symlink stored there is listed with no target (`reason="target_data_unsupported"`, §6) | **library** | The folder is valid: the format allows `lc + lp` up to 12 and 7-Zip decodes it. liblzma, which stdlib `lzma` wraps, decodes `lc + lp` up to 4 only (`LZMA_LCLP_MAX`) and fails the rest with `LZMAError: Internal error`. Left unsupported by maintainer decision, 2026-10-08 (§6). ZIP LZMA members behave the same ([`zip.md`](zip.md) §5) |
| A byte 1 MiB or more past the archive's end goes unreported | **archivey** | The trailing-data scan is an effort bound, not a guarantee (§2.2), the same bound as TAR's ([`tar.md`](tar.md) §5) |
| A zero-padded `.7z` opens silently here, and 7-Zip warns "There are data after the end of archive" | **archivey** | DR-3 keeps an all-zero tail silent for every format. 7-Zip warns about any tail. No 7z writer pads; the rule is TAR's, kept the same everywhere so `STRICT` means one thing |

## 6. Decisions

| Choice | Why | Rejected |
| --- | --- | --- |
| Under rapidgzip, check a Deflate coder's end from the last point of rapidgzip's complete index (2026-10-24) | As for a ZIP DEFLATE member ([`zip.md`](zip.md) §6): the cost of the tail where the index has a point before the end (with none, the check decodes from the start and costs what it did before), and the same result on every run on one machine. A long second Deflate stream that holds the point and that the unpack size covers then may read as content (DR-5a) | A zlib decode from the start, or a parallel check between resume points (about 300 ms on 40 MiB), both costing about what the read without rapidgzip costs |
| Native header parser plus shared codec streams | Solid-folder access under our own cost model, and no third-party quirks leaking into the unified contract; reading common codecs stays in the zero-dependency core | Wrapping `py7zr`, whose per-folder caching made "iterate and hash every member" intractable — kept as a dev oracle (ADR [0001](../decisions/0001-native-7z-not-py7zr.md)) |
| Decode BCJ2 in pure Python | It keeps memory bounded, names the failing stream, needs no new dependency, and works through the existing AES stage | `pylzma.bcj2_decode` (30–60× faster, but whole-buffer, allocates the declared size up front, LGPL with no Linux wheel); `libarchive-c`, a second 7z reader that cannot open encrypted 7z; refusing BCJ2, which is what `-mx9` writes |
| Find BCJ2 branch candidates with `bytes.find` over a translated block | Two literal searches run at memchr speed; a regex character class scans byte by byte in `re` and cost as much as the rest of the loop | The prototype's `[\xe8\xe9]\|\x0f[\x80-\x8f]` regex, about half the speed |
| Accept a tree of linear chains, not a general graph | Every archive the CLI writes is a tree: linear, or BCJ2 fed by linear branches. A graph that shares an output needs buffering, which is a decode engine, not a planner | Executing arbitrary coder graphs; special-casing 7-Zip's BCJ2 coder order, which the encrypted layout already breaks |
| Branch filters through liblzma, not `pybcj` | Two `pybcj` defects return wrong bytes on ordinary archives: a signed 32-bit unpack size, and IA64 dropping the trailing partial block | Keeping `pybcj` and working around both; it is no longer imported and is out of `[recommended]` |
| Stage LZMA1+BCJ separately, always | Measured truncation through a single combined chain on 20 of 24 CLI-written archives, re-measured 2026-09-19 because one chain would be faster on this shape | One raw chain, which is correct for LZMA2 and wrong here — the BPO-21872 fix is a different code path and does not license collapsing it |
| Treat a decoded header with zero file records as a wrong password | No legitimate writer encrypts an empty header, and the alternative is reporting an empty archive to a backup checker | Accepting it; adding a `num_files` sanity field the format does not have |
| Cap `NumCyclesPower` at 24 | Matches 7-Zip's own decoder clamp, so nothing readable elsewhere is refused here, and it bounds one derivation's cost | Deriving whatever the archive asks for; a time-based cutoff, which depends on the machine |
| Confirm a password by decoding and CRCing in chunks | The format offers nothing cheaper, and materialising the folder peaked at about three times its size | Materialising the folder; skipping confirmation and handing back unverified bytes |
| Stop confirmation at the earliest 4-byte anchor, and at 64 KiB for a rejecting codec | The correct password paid a full folder decode before this, and a wrong key dies in LZMA or BZip2 within a few bytes | Walking every CRC to the folder end; one decoded byte as the budget, which a decoder change of a few bytes could flip; running candidates in lockstep, which shares only the source read |
| List an anti item, write nothing for it, and delete only what this run wrote | Deleting a destination file the archive never wrote is not something an extraction should do unasked; deleting one the same run just wrote keeps `results` from advertising content that is gone | Honouring the tombstone against a path this run never wrote; hiding the item, which would make an incremental archive's history unreadable |
| `max_members` bounds unpack streams; the coder-graph cap does not | A solid archive's unpack-stream count *is* its member count, so the structural cap refused ordinary 7-Zip output (O13) | One cap for both; capping pack streams by member count, which refuses non-solid BCJ2 |
| Leave LZMA1 `lc + lp` over 4 unsupported | 7-Zip writes it only when asked (`lc=8`). Decoding it needs an LZMA1 decoder other than liblzma | `pylzma` 0.6.1, which binds 7-Zip's own LZMA SDK and does decode these (an `lc=8` ZIP member read back byte-identical, one-shot and through `decompressobj`), but ships only an sdist (a C compiler for every install) under the LGPL, the reasons it was rejected for BCJ2 too; a pure-Python LZMA1 decoder (very slow); handing such members to the `7z` CLI (archivey has no 7z CLI backend). `backports.lzma` and libarchive both use liblzma |
| The archive ends at the later of the next header's end and the last packed stream's end | 7-Zip writes the packed streams first, so this is the next header's end on every archive it writes. Readers follow `PackPos`, so a header written first still reads; counting only the header would report the member data the listing just read as trailing | The next header's end alone; refusing a header-first layout as 7-Zip 23.01 does ("Headers Error"), which is a behaviour change of its own |
| Bound the trailing-data scan at 1 MiB, as a constant | The same bound and reasoning as TAR's ([`tar.md`](tar.md) §6): a constant can become a config field later, a field cannot become a constant | Scanning to EOF; a `ListingLimits` field |
| A symlink whose target data cannot be decoded is listed with no target | One member's data says nothing about the others (DR-2, and DR-5 for a missing library), and listing reads every symlink's target. A folder this reader does not decode (LZMA1 `lc + lp` over 4, an unsupported coder) or one whose optional library is not installed (PPMd without `pyppmd`) made `members()`, `stream_members()` and `extract_all()` fail for the whole archive. The link is reported (`target_data_unsupported` or `package_not_installed`) and raises that error when opened or extracted; a strict policy refuses the archive, even when only a library is missing. The handling is the shared base hook's, as for ZIP ([`zip.md`](zip.md) §6) | Raising from `members()`, which took every other member with it |

## 7. Open questions

- **Whether eager link-target resolution should be deferred for solid folders.** Making
  `link_target` lazy would let a caller list a solid archive without decoding it, at the
  cost of a listing where some members' targets are not yet known; the cheaper answer is
  to say so in `CostReceipt.notes` at open, the way the RAR backend flags its temp-file
  copy, and change nothing else. What would answer it: whether any caller reads
  `link_target` for every member anyway, which the extraction path nearly does. Tracked
  internally.

**The solid-listing cost has no test.** The corpus sweep asserts that a 7z symlink's
target is read correctly; no test asserts how much was decoded to read it. So if
`_ensure_link_target` stops being eager — which is what §7's third question proposes — the
sweep catches it on the target and nothing catches it on the cost: a lazy resolve leaves
`link_target` unset at listing, which fails the sweep's `symlinks` entry, while the folder
decode that entry no longer performs goes unnoticed. That guard is not universal: it needs
py7zr to build the fixture, so it is absent under `[core-only]`, and the corpus skips its
7z symlink entries on Windows, where creating a symlink needs privileges. Until a cost
test exists, this is the reproduction:

```python
import archivey
from archivey.internal.measurement import enable_measurement

# 7z a -snl solid.7z f1..f5.txt link.txt   (five equal files, the symlink written last)
# 7z a -snl -ms=off nonsolid.7z <the same>
#
# -snl is load-bearing: without it 7-Zip stores link.txt as an ordinary file, so neither
# archive holds a symlink, the listing resolves no target, and both print 0. Measured:
# 0 against 0, which reads as a broken harness rather than as the wrong fixture.
with enable_measurement():
    for name in ("solid.7z", "nonsolid.7z"):
        with archivey.open_archive(name) as archive:
            archive.members()                    # listing alone, nothing opened
            stats = archive.io_stats()
            assert stats is not None             # None if opened outside the with block
            print(name, stats.bytes_decompressed)
```

Measured on five 27 019-byte members plus the link: **135 101** bytes for the solid
archive — its whole folder — against **6** for the non-solid one, which is the link target
and nothing else.

**Building fixtures.** Most fixtures shell out to the `7z` CLI and skip when it is absent
— one of the ~109 tests that vanish quietly on an unprovisioned container, so read the
session-setup script's closing verification block. `-m0=` / `-m1=` select the coder chain
(`-m0=BCJ -m1=LZMA` for the staged case, `-m0=BCJ2 -m1=LZMA -m2=LZMA -m3=LZMA` for BCJ2),
`-ms=off` makes an archive non-solid, `-mhe=on` encrypts the header, and `-v` writes a
split set. Shapes the CLI will not write are built by hand: the anti-item archive is
synthesised byte by byte as well as produced through `7z u`, and the header-bomb inputs
are assembled from the property tags directly. `tests/fuzz_sevenzip_parser.py` is the
Atheris harness over the parser. `tests/test_py7zr_corpus.py` runs against py7zr's own
`tests/data` when `ARCHIVEY_PY7ZR_TEST_FILES` points at it, and is off by default.
