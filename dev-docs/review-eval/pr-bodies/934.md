# Drop a seek index that the stream's own decode contradicts, and warn

_Requested by **davi** · [project thread](https://claude.ai/code/project/chan_01DbMk7aw1GQgNkBfBSYo2X2?thread=cmsg_01DbMk7aw1GQgNkBfBSYo2X2E5rKchnRpFdSNTq6Qp5Vid)_

Found in the sweep of features merged since 0.2.0rc1 (its seek docs part landed as #930). Behaviour as ruled by the maintainer on 2026-10-20: drop the index and warn, never refuse the file.

## Before

A Seekable Zstandard seek table or a BGZF member's BSIZE could give a unit the wrong decompressed size while the compressed sizes still added up. The stream then held two seek points at the same compressed offset with different decompressed offsets: one from the index and one recorded by the forward decode. Nothing compared them. So a later seek could use the index's point and return another unit's bytes with no error, even after a full forward read had recorded the true point (zstd, four frames: a seek to 150 returned `BBBB` instead of `AAAA`). A BGZF size query could also report one size and a later read another.

When the index and the decode instead put one decompressed offset at two compressed offsets, the stream raised `CorruptionError`, but only if a size query had read the index first, so the outcome depended on call order. The same raise refused an honest lzip file with an empty member whenever its trailer index was read.

## After

- Seek points from an index scan, and points recorded by a decode that resumed at one, are marked as the index's (`SeekPoint.from_index`, not part of comparisons).
- Two cases count as a contradiction: a point with the same compressed offset and resume state as another names a different decompressed offset; or a decode reaches the end with a different total than the index gave, which catches a lie in the last unit, where no index point follows.
- On a contradiction the stream drops every index point and any size the index gave, emits `SEEK_INDEX_DEGRADED` once (scan `decode_check`, error type `SeekIndexContradicted`), and from then on seeks only from points found by decoding. If the decoder in use had resumed at an index point, the stream restarts it from a decoded point before the read, seek or size query returns, so that call returns the right bytes. Under STRICT the report is raised once the stream is consistent, so a caller can catch it and keep reading.
- The check compares only points the seek table holds, so its memory is bounded by `MAX_SEEK_POINTS`. After a thinning, a lie at a unit start the table dropped is caught at the next start it kept, or at the end.
- The stream counts the decoder's output position itself, so the size set at the end of `readall` is never briefly too small (which would have looked like a contradiction on honest files).
- **A change beyond the ruling, to the existing collision raise:** when an index point and a decoded point share a decompressed offset with different compressed offsets, the decoded point is now kept and nothing is raised (of two index points, the later compressed offset wins). That pair does not prove a lie: an honest lzip file with an empty member produced it. This fixes that refusal and the call-order split. The raise stays for different non-None states (xz block records) and for two decoded points.
- Still not caught (O17): bytes returned, and a size the index gave, before the decode reaches the contradicting unit start or the end; and a size asked only after a read to the end, since the index is then never read (reading it just to compare would be a second full pass for BGZF). Sizes and bytes after a full read are the same in both orders.
- `dev-docs/threat-model.md` O17 says exactly what is caught and not; the seekable-decompressor-streams spec gains requirement text and scenario rows; the zstd and gzip handbook pages get a sentence each.

## Tests

- `tests/test_zstd_seekable.py`: a forward read contradicts the table and a later seek to 150 returns frame 0's bytes; a seek into a misplaced frame drops the table and reads right; a lie about the last frame is caught by the decoded total; a size from a contradicted table is forgotten and recomputed; under STRICT the report raises once and reading on returns every byte.
- `tests/test_bgzf_seek.py`: a member whose BSIZE hides the next member reads right (including at 10005) and the size matches the decoded one; the same-decompressed-offset variant reads the same with or without a size query first; a hidden last member is caught by the decoded total, in one read and in pieces, in both call orders (one report size-first, none read-first); the thinning test asserts the check stays within the seek-point cap after a full read.
- `tests/test_seekable_streams.py`: an lzip file with an empty member reads correctly in both orders with no diagnostic.
- Every new test fails without this change and passes with it, except the read-first hidden-last-member case, which expects no report. The full suite passes; `check.sh` (with `openspec validate --all`) is clean.
