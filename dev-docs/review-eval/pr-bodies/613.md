# rapidgzip: keep the gzip length check through seeks and chance header matches; hand seeks over on data errors; first zlib stream only

_Requested by **davi** · [project thread](https://claude.ai/code/project/chan_01DbMk7aw1GQgNkBfBSYo2X2?thread=cmsg_01DbMk7aw1GQgNkBfBSYo2X2V9nEJpLy53RxG9m6v636No)_

Before: under the rapidgzip accelerator (default `AUTO` for a `.gz` of 16 MiB or more with `seekable_members=True`, or `ON`), any seek on a `.gz`, even back to 0, turned off the check that compares the decoded length with the ISIZE trailer, so a cut file read short with no error. A length mismatch was also ignored whenever `1f 8b 08` appeared anywhere in the file, which a compressed body contains by chance about once per 16 MiB, so on most large files a cut or wrong-ISIZE `.gz` went unreported (measured: a 17 MB `.gz` cut by 2.7 KB read short and clean). A seek that met NUL padding after a valid `.gz` raised `CorruptionError`. A `.zz` holding two zlib streams read as one under `ON`, where the standard library reads the first and reports the rest as trailing data.

After: a cut, wrong-ISIZE or padded `.gz` gives the same result with `use_rapidgzip=ON` as with `OFF`, before or after seeks: `TruncatedError`, the checksum error, `ARCHIVE_TRAILING_DATA`. A whole-member read or a seek to the end of a two-stream `.zz` returns the first stream and reports the rest as trailing data. Bounded reads that already returned bytes past the first zlib stream still read both, because those bytes cannot be taken back; `AUTO` never accelerates zlib, so this is `ON` only, and it is documented.

These came out of a cross-format check of recent bugs: the seek gap is the C4 "re-check after a seek back to 0" ruling not reaching this path, and the seek handover is the one bzip2 got in #563.

How: the gzip check compares the position of the read that meets the end of rapidgzip's output instead of a byte count that a seek reset. A `1f 8b 08` counts as a further member only when zlib's gzip decoder accepts the header and decodes from it (to the member's end with CRC and ISIZE, or 64 KiB in / 1 MiB out), within a shared budget of 1 MiB plus 1/16 of the bytes scanned; otherwise the read goes to the standard library, which gives the verdict. A real multi-member file (bgzip) still stands down without a second decode. Seeks in the DEFLATE family hand over on data errors as bzip2's already did, so the `seek_takes_over` parameter is gone; errors from the caller's own source still pass through. The zlib Adler-32 confirmation hands over at the end of the first stream when the caller has nothing past it.

Tests: new `tests/test_rapidgzip_end_checks.py` (47 tests) compares accelerator ON with OFF for each case on payloads of about 1 MB; 24 fail on main. `test_rapidgzip_zlib_concatenated_streams_pass_the_check` pinned `read()` returning both zlib streams and now expects the first. Docs: `dev-docs/formats/gzip.md`, and `openspec/specs/seekable-decompressor-streams/spec.md` (three matrix rows).

**Review round 1 (follow-up commit):** Round 1 (no further round needed) raised one real bound problem and seven wording and documentation gaps; all eight are fixed in `37419bd1`. The member probe asked zlib for the full 1 MiB on every call while counting output across calls, so one candidate could decode almost 2 MiB. Each call now asks only for what the bound leaves, and a new test pins exactly 1 MiB. The seek test that still asserted the removed disarm rule now asserts the new contract: after a seek, a cut file still raises `TruncatedError` and an intact file reads in full. Comments on the replaced further-magic rule, the `switch_to_stdlib` callers, why `_pos` is kept, and the first-zlib-stream handover slice now match the code; the probe constants say why they are not config limits. The gzip handbook row and the `seekable-decompressor-streams` spec now say that a two-stream `.zz` read under `ON` in bounded reads reports no `ARCHIVE_TRAILING_DATA`.
