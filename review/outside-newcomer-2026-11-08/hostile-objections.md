# archivey hostile objections

## O1: There is no single, stable contract for declaring an archive acceptable

- Argument: The caller has to reconstruct success from exceptions, member results, listing errors and diagnostics. A completed extraction can have rejected entries; an empty verification failure list can coexist with a broken archive. These distinctions are legitimate internally, but making every application assemble them is a poor public boundary. Worse, the convenience API for verification is explicitly experimental. A year into operating an importer, an engineer can still be maintaining an application-owned acceptance engine whose dependencies may change in a patch release. I would prefer a narrower library with an explicit acceptance contract over a broader one that makes this decision so easy to get wrong.
- Evidence: **Ran in the earlier review, archivey 0.3.0:** `verify_all()` returned `[]` for the generated truncated ZIP while `members_report().error` contained `TruncatedError`; traversal extraction returned normally with a blocked result. **Fresh docs read:** [Errors and diagnostics → Damaged archives](https://archivey-dev.github.io/archivey/errors-and-diagnostics/#damaged-archives) requires checking member failures, the listing report and diagnostics; its Experimental notice allows changes in “any release, a patch release included”. [Extracting → Options](https://archivey-dev.github.io/archivey/extracting/#options) says: “A refused member isn't a failure”. These are documented contracts, not newly discovered bugs.
- Who it hurts: Upload validators, package importers, backup checks and ingestion jobs that must distinguish complete acceptance from salvage. It also hurts teams expecting patch upgrades to preserve their verification code.
- Fix: Add a stable `validate()` returning one immutable `ValidationReport` with an explicit overall outcome, structural completeness, unchecked data and member failures. Give it a `raise_for_failure()` method and explicit acceptance criteria. Extraction should expose the same outcome vocabulary and attach partial results to exceptions. Preserve salvage as an explicit mode.
- Cost to change: **Medium.** A parallel API can be additive; changing existing methods' return shapes or rejection defaults would break callers. The new acceptance contract must be covered by the normal compatibility promise.
- Strongest counter-argument the maintainers could make, and why you still hold the objection: Damaged archives are not binary, and diagnostics preserve valuable distinctions. Agreed: the report should retain every distinction. That does not justify requiring each consumer to rediscover how those distinctions combine into an application decision. A richer result object can preserve detail while making incomplete verification impossible to mistake for success.

## O2: A member object can change what kind of thing it represents after you have processed it

- Argument: `ArchiveMember` looks like metadata an application can inspect and act on, but streaming can make it provisional in fundamental ways. The same object can change from a file to a symlink, or from the current version to a superseded version. A generic consumer can therefore make a locally reasonable decision using `is_file` or `is_current` that the library later revises. Updating the retained object cannot retract an upload, database insert or downstream event already emitted. This is a mismatch between an object-shaped API and an event stream whose meaning is not final yet.
- Evidence: **Freshly ran on 0.3.0:** fed the self-generated symlink ZIP through a nonseekable `io.RawIOBase` wrapper with `streaming=True`. During `stream_members()`, the `link` entry had `type='file'` and `member_state_final=False`; after exhaustion the same object had `type='symlink'` and `member_state_final=True`. A generated duplicate-name ZIP yielded both versions with `is_current=True`; afterward their flags were `False, True`. **Fresh docs read:** [Choosing how to read → Reading once](https://archivey-dev.github.io/archivey/reading/#reading-once) explicitly says “a symlink looks like a file”; [Opening an archive → Members with the same name](https://archivey-dev.github.io/archivey/opening/#members-with-the-same-name) describes the later updates. The built-in extractor stages ZIP data; I am criticizing consumers of the public stream API, not claiming an extraction escape.
- Who it hurts: Streaming scanners, indexers, event pipelines and code passing member metadata between components or threads. The problem appears when supporting pipes after development against ordinary files.
- Fix: Separate provisional stream events from immutable, finalized members. Use an explicit unknown type until classification is known, and distinct finalization events rather than retroactively changing previously yielded records. Offer staging for callers requiring final metadata before processing. Represent duplicate selection as a policy or finalized view, not a temporarily authoritative boolean.
- Cost to change: **High.** Changing member mutability or streamed types breaks consumers, selectors and equality assumptions. Introduce a separate event API first and deprecate the ambiguous path gradually.
- Strongest counter-argument the maintainers could make, and why you still hold the objection: ZIP metadata physically arrives late; `member_state_final` exposes that honestly, and staging sacrifices immediate streaming. The format constraint is unavoidable. Giving uncertain metadata the same ordinary member shape as final metadata is avoidable. Callers should have to opt into provisional events rather than remember to distrust otherwise useful fields.

## O3: The common API hides radically different cost models without enforcing a safe default for named reads

- Argument: `read(name)` looks like the same operation across formats, but on solid archives it can mean decoding a growing prefix again. Repeating it can turn a straightforward file-processing loop into potentially quadratic decompression work. That complexity is an inference from repeated prefix decoding, not a benchmark result from this review. The API exposes the cost and offers an efficient alternative, yet defaults to permitting the expensive pattern. The uniformity is also selective: concurrent member streams are prohibited even where the format supports them efficiently. Users inherit both hidden slow paths and extra state restrictions.
- Evidence: **Docs only for repeated-read complexity and concurrency:** [Choosing how to read → Solid archives](https://archivey-dev.github.io/archivey/reading/#solid-archives) says reaching a solid member means “decompressing others first”. Repeated work on solid 7z/RAR produces an INFO log only when enabled. The same page documents `archive.cost`, one-pass `streaming=True`, and the single-open-stream default under Several members at once. **Previously ran:** archive-order streaming hashed all 17 files in the generated 1.0625 GiB tar.gz correctly with modest memory. That proves the efficient path works; it does not make the default named-read path efficient.
- Who it hurts: Applications accepting unknown formats, especially those initially tested on ZIP, and libraries that need two members open together. The cost often emerges only with large customer archives or after adding parallel processing.
- Fix: Separate forward traversal from indexed access with explicit reader interfaces or capability objects. Require an explicit option to permit prefix redecoding, or make repeated expensive reads warn prominently. Make bulk member selection a first-class operation so callers can request many names without planning decompression order themselves.
- Cost to change: **High.** Making expensive named access opt-in would break working callers; capability interfaces can first be added without removing the existing facade. Existing cost metadata provides a useful migration foundation.
- Strongest counter-argument the maintainers could make, and why you still hold the objection: Compression formats impose these costs, and `archive.cost` plus `stream_members()` already teach callers how to avoid them. True. The objection is that code must inspect the format's cost model to use the supposedly common API responsibly, while the default accepts the expensive operation. Exposing a hazard and making callers opt into it are different design choices.

## O4: The limit system does not express the resource budget an untrusted-input service actually needs

- Argument: There are useful limits for extraction output, metadata, decoder allocations, ratios and temporary files, but they do not combine into one workload budget. An incompressible member can evade a ratio-based read bound; multiple concurrent decoders consume memory independently; nested archives receive separate allowances; elapsed time needs an external process boundary. Consequently, an application that moves from extracting uploads to scanning them must build another resource-control layer despite already configuring archivey's limits. The missing abstraction is a shared budget for the whole job, not another generous default constant.
- Evidence: **Ran in the earlier review:** with `max_extracted_bytes=1024`, `read('data')` returned all **8,388,608 bytes** of a generated incompressible ZIP member. **Fresh docs read:** [Security → Where the guarantees stop](https://archivey-dev.github.io/archivey/security/#where-the-guarantees-stop) states “Reading a member has no byte cap.” The same section explains independent per-archive limits, concurrent decoder memory and the absence of operation time limits. [Hardening](https://archivey-dev.github.io/archivey/security/#hardening) documents a default 2 GiB decoder allocation allowance. These documented constraints were not all experimentally exercised.
- Who it hurts: Multi-tenant upload services, recursive archive scanners and workers running under container memory limits. It hurts most when several individually permitted operations share one worker or job.
- Fix: Add an optional shared `ResourceBudget` propagated explicitly to nested readers and concurrent operations, with cumulative decoded-byte and work allowances. Provide bounded whole-member reads and a documented worker-process integration for hard memory/time enforcement. Separate logical budget guarantees from operating-system containment; do not claim a Python object alone can impose a hard RSS ceiling.
- Cost to change: **Medium.** An opt-in shared budget and bounded-read API can be additive. Finite read caps or mandatory budget sharing as defaults would break existing large-read workloads.
- Strongest counter-argument the maintainers could make, and why you still hold the objection: No in-process archive library can guarantee CPU time or total process memory, and applications own their deployment limits. Correct. I would still expect the library to account for the bytes and repeated work it performs across its own operations. A shared logical budget plus honest process-level guidance would substantially reduce duplicated application code without promising impossible isolation.

## O5: The parser and execution policy depends too much on what happens to be installed

- Argument: Installing an unrelated optional package can expand the code that parses the same input; accelerator selection can depend on platform and stream properties; RAR decompression can depend on executables found on `PATH`. That makes the deployed environment part of the input-processing contract. Pinning archivey alone does not freeze that contract. A team seeking reproducible validation must maintain package exclusions, format allowlists, accelerator settings and executable selection together. The unifying dependency becomes a policy dispatcher over an expanding dependency graph, which is a substantial long-term ownership cost.
- Evidence: **Docs only; no fresh backend-difference or RAR experiment:** [Security → Hardening](https://archivey-dev.github.io/archivey/security/#hardening) says optional packages can be used “even one installed system-wide that your program doesn't depend on”. It documents external RAR selection and format/library exclusions. [Choosing how to read → The same result everywhere](https://archivey-dev.github.io/archivey/reading/#the-same-result-everywhere) documents exceptional crafted inputs for which accelerator results can differ with platform or core count, plus explicit opt-out settings. [Opening an archive → Configuration](https://archivey-dev.github.io/archivey/opening/#configuration) explains that a container-format exclusion is not a general prohibition of that codec inside another container. I am not claiming ordinary archives commonly differ.
- Who it hurts: Reproducible build systems, forensic processing, services with multiple deployment images, and teams whose dependencies or system utilities change independently of application code.
- Fix: Offer a supported deterministic profile with an explicit backend allowlist, explicit external-tool paths and a machine-readable resolved execution plan. Reject undeclared backends in that profile. Document one complete configuration recipe that freezes parsing policy, including how container and codec permissions differ. Keep automatic discovery available for interactive use.
- Cost to change: **Medium.** An opt-in profile and backend manifest would be additive. Making it the default would break automatic format availability, acceleration and external-tool discovery for existing users.
- Strongest counter-argument the maintainers could make, and why you still hold the objection: Optional discovery is convenient, current controls already permit much of this, and other archive libraries also depend on native code or system tools. Agreed. The objection is the absence of one supported, auditable configuration boundary. If reproducibility requires assembling scattered controls and remembering which ones govern containers versus codecs, the application still owns the policy integration that a unifying library ought to simplify.

## What I would keep

1. Content-based format detection and a consistent vocabulary for member metadata.
2. A first-class archive-order streaming API that can process large solid archives without buffering every member.
3. Extraction containment checks, structured refusal reports and configurable resource guards; the malicious fixtures tested did not escape.
